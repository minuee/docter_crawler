# 제미니(Gemini) 의사 이력 분석 가이드 (v4)

**⚠️ 제미니(Gemini) AI 에이전트의 역할 및 행동 지침 ⚠️**

이 문서는 `crawling_did_link/route.js`의 `find-past` API에서 동명이인 의사의 과거 이력을 분석하고 판별하기 위한 제미니 AI 에이전트의 행동 규칙을 정의합니다.

**✅ AI 에이전트의 역할:**

*   `find-past` API 호출 결과로 생성되는 `services/crawling_did_link/data/[HOSPITAL_ID]/ai_analysis_request_*.json` 형태의 JSON 파일을 검증하는 작업만을 수행합니다.
*   이 검증 작업은 아래 정의된 "분석 규칙"에 따라 `match` 또는 `notmatch` 여부를 판단하고, 그 결과에 따라 JSON 파일 내용을 수정하거나 파일명을 변경하는 것을 포함합니다.

**🚫 AI 에이전트의 금지 사항:**

*   `doctorCompare.js` (또는 이와 유사한 기존 코드 파일)를 **절대 수정하지 않습니다.** 이 파일들은 AI 에이전트의 작업 대상이 아닙니다.
*   `find-past` API를 통한 JSON 파일 검증 작업 외의 다른 API (`/find-past-resume`, `/update-notexist`, `/save-notmatch`, `/save-match`, `/second-check`) 또는 관련 로직에는 **절대 개입하거나 수정하지 않습니다.** 이러한 작업은 사용자(인간)의 수동 작업 영역입니다.
*   사용자의 명확한 지시 없이는 `web_fetch`와 같은 도구를 사용하여 외부 네트워크에 접속하거나 페이지 내용을 분석하지 않습니다. (특히 3.6단계 관련)

---

## 분석 목표

`summaryData`(대상 의사) 정보와 `summaryData2`(동명이인 목록)를 비교하여, `summaryData2`에서 `summaryData`의 **과거 이력에 해당하는 의사 1명을 정확하게 찾아냅니다.**

## 분석 규칙 (판단 우선순위)

분석은 아래 필터링 단계를 순차적으로 거칩니다. 각 단계를 거치며 후보 목록을 좁혀나가고, 최종적으로 1명을 선택합니다.

### 0단계: 동일 병원(`hospitalname`, `hid`) 최우선 매칭

*   `summaryData2` 목록에서 `summaryData`와 `hospitalname` 및 `hid`가 모두 동일한 후보가 있다면, 해당 후보를 **최종 결과로 확정**하고 분석을 즉시 종료합니다.
*   이 단계에서 매칭되는 후보가 2명 이상인 경우는 없다고 가정합니다.

### 1단계: 진료과(`deptname`) 필터링

*   `summaryData2` 목록에서 `summaryData`와 **`deptname`(진료과)이 동일한** 후보만 남깁니다.
*   이 단계 후 후보가 0명이면, "매칭 실패"로 분석을 종료합니다.

### 2단계: 진료분야(`specialties`) 유사도 필터링

*   1단계를 통과한 후보들을 대상으로, `summaryData`의 `specialties` 필드와 각 후보의 `specialties`를 비교하여 '유사도 점수'(겹치는 항목 수)를 계산합니다.
*   가장 높은 '유사도 점수'를 가진 후보들만 남깁니다.

### 3단계: 과거 근무 이력 교차 확인 (합리적 의심)

*   2단계를 통과한 후보들을 대상으로, `summaryData`의 `info` 필드(학력/경력 정보)를 분석하여 **과거 근무 병원 및 진료과 정보**를 추출합니다.
*   후보의 `hospitalname` 및 `deptname`이 `summaryData`의 과거 근무 이력과 일치하는 경우, 해당 후보를 **강력한 잠정 후보**로 간주합니다.
*   이 경우, 후보의 `info` 필드가 비어 있거나 정보가 부족하더라도, `summaryData`의 `info`에 명시된 과거 근무 이력과 후보의 현재 병원/진료과 정보가 일치한다면, 동일인물일 가능성이 매우 높다고 판단하여 **3.5단계**로 넘어갑니다. (즉, `info` 필드의 내용 유사성 판단을 우회할 수 있는 강력한 근거로 활용합니다.)
*   이 단계에서 강력한 잠정 후보가 1명만 발견되면 해당 후보를 **잠정 후보**로 선택하고 **3.5단계**로 넘어갑니다.
*   여러 명의 강력한 잠정 후보가 발견되거나, 이 단계에서 후보가 발견되지 않으면 다음 **3.1단계**로 넘어갑니다.

### 3.1단계: 상세 정보(`info`) 내용 유사도 및 기간 일치 필터링

*   3단계를 통과한 후보들을 대상으로, `summaryData`의 `info` 필드(학력/경력 정보)와 각 후보의 `info` 필드를 비교하여 내용의 유사성과 기간의 일치 여부를 판단합니다.
*   **유사성 판단 기준:**
    *   `summaryData`의 학력/경력 항목 중 최소 1개 이상이 후보의 학력/경력 항목과 내용적으로 일치해야 합니다. (예: 동일 기관, 유사한 직책/학위, 겹치는 기간)
    *   후보의 학력/경력 기간이 `summaryData`의 학력/경력 기간보다 선행하거나 겹치는 부분이 있어야 합니다. (즉, 후보가 `summaryData`의 과거 이력일 가능성이 높아야 함)
*   위 기준을 만족하는 후보들만 남깁니다.
*   이 단계 후:
    *   후보가 0명이면, "매칭 실패"로 분석을 종료합니다.
    *   후보가 1명이면, 해당 후보를 **잠정 후보**로 선택하고 **3.5단계**로 넘어갑니다.
    *   후보가 2명 이상이면, 그 중에서 `summaryData`의 `info`와 가장 많은 학력/경력 항목이 겹치고 기간적으로 가장 적합한 (가장 오래된 이력을 포함하는) 후보 1명을 **잠정 후보**로 선택하고 **3.5단계**로 넘어갑니다.

### 3.5단계: 프로필 이미지 유사도 분석 (보조)

*   `summaryData`와 3단계를 통과한 후보의 `profileimgurl`이 유효한 이미지 주소(기본 'no image'가 아닌)를 가리키는 경우에만 이 단계를 수행합니다.
*   각 프로필 사진에 나타난 인물의 외모(성별, 추정 연령대, 헤어스타일, 안경 착용 여부 등)를 텍스트로 묘사합니다.
*   묘사된 텍스트를 비교하여 두 인물이 동일인일 가능성이 높은지 판단합니다.
*   이 분석 결과는 다른 정보(진료과, 경력 등)와 함께 최종 판단의 보조 자료로만 활용하며, 결정적인 기준으로 삼지는 않습니다.
*   이미지 분석 후 다음 **3.6단계**로 넘어갑니다.

### 3.6단계: 과거 정보 `doctor_url` 유효성 검사 (필수)

*   3단계를 통과한 잠정 후보(과거 이력으로 추정되는 의사)의 `doctor_url`을 검사합니다.
*   `doctor_url`에 접속하여 해당 페이지가 정상적으로 열리고 현재까지 해당 의사의 프로필을 활발하게 보여주는지 확인합니다.
*   **판단 기준:**
    *   만약 `doctor_url`이 정상적으로 접속되고 해당 의사가 현재까지 그 병원에 재직 중인 것으로 명확히 확인된다면, 이는 `summaryData` 의사의 과거 이력으로 보기 어렵습니다. 이 경우 해당 후보는 "매칭 실패"로 간주하고 분석을 종료합니다.
    *   `doctor_url`이 더 이상 존재하지 않거나, 해당 의사가 목록에서 사라졌거나, 이직 사실이 명시되어 있는 경우에만 과거 이력 후보로 유효하다고 판단하여 **4단계**로 넘어갑니다.
    *   **⚠️ AI 에이전트의 기술적 한계 및 처리 방안:** AI 에이전트는 `web_fetch`와 같은 도구를 직접 호출하여 웹 페이지 내용을 이해하고 의사의 재직 여부를 판단하는 데 제한적입니다.
        *   **기본 처리:** 이 단계는 AI 에이전트가 직접 수행하지 않습니다. `doctor_url`의 유효성 검증은 **수동 검토 영역**으로 간주하며, AI는 이 단계를 항상 통과한 것으로 가정하고 다음 단계로 진행합니다.
        *   **예외 처리 (사용자 지시 시):** 만약 사용자(인간)가 AI 에이전트에게 `browser_web_fetch`와 같은 도구를 사용하여 `doctor_url`을 확인하도록 명확하게 지시하는 경우에만, AI는 제한적으로 웹 페이지 내용을 가져와 키워드 분석을 시도할 수 있습니다. 이 경우에도 분석 결과가 불확실하면 "매칭 실패"로 처리될 수 있습니다.

### 4단계: 최소 정보량 원칙 (최종 판별)

*   3단계에서 선택된 잠정 후보와 대상 의사의 정보를 최종 비교합니다.
*   만약 **대상 의사와 잠정 후보 모두의 `info` 필드 문자열 길이가 10 미만**이라면, 정보 부족으로 최종 판정을 **"매칭 실패"**로 내립니다.
*   그렇지 않은 경우, 잠정 후보를 **최종 결과로 확정**합니다.

### 최종 결과 확정 시 파일 포맷 (AI 에이전트용)

**`match` (일치) 로 확정된 경우:**

기존 `summaryData`와 `summaryData2`를 그대로 유지하면서, **최상위 레벨에 `isResult` 객체를 추가**합니다. 파일은 `summaryData`, `summaryData2`, `isResult` 세 개의 키를 가져야 합니다.

*   **`isResult` 객체 구조:**
    ```json
    "isResult": {
        "result": "match",
        "userInfo": {
          // 중요: 여기에 매칭된 과거 이력 의사의 모든 정보 (summaryData2 내의 해당 후보의 전체 내용)를 입력해야 합니다.
          // 절대 summaryData의 내용을 복사해서는 안 됩니다.
          "info": "[...]",
          "hospitalname": "...",
          "hid": "...",
          "deptname": "...",
          "doctorname": "...",
          "specialties": "...",
          "rid_long": "..."
        }
    }
    ```
*   **올바른 최종 파일 구조 예시:**
    ```json
    {
      "summaryData": { ... },
      "summaryData2": [ ... ],
      "isResult": {
        "result": "match",
        "userInfo": {
          // 매칭된 과거 이력 의사의 정보
        }
      }
    }
    ```

### 최종 결과 `isResult` 객체 생성 시 주의사항
*   **항상 유효한 JSON 형식을 유지해야 합니다.**
*   `userInfo` 객체에 포함되는 `info` 필드는 원래 데이터의 JSON 문자열 형식을 그대로 유지해야 합니다. **문자열 자체를 복사**해야 하며, 문자열 내의 따옴표나 특수문자가 깨지지 않도록 주의해야 합니다.

## `notmatch` (불일치) 처리 규칙 (AI 에이전트용)

`find-past` API를 통해 생성된 파일을 분석한 결과, `summaryData2` 목록에 적합한 과거 이력이 없다고 판단될 경우, 다음 단계를 반드시 수행해야 합니다.

1.  **파일명 변경:**
    *   분석한 파일의 이름 끝에 `_notmatch`를 추가합니다. (예: `..._박영주.json` -> `..._박영주_notmatch.json`)

**참고:** 파일 내용은 변경하지 않습니다. `summaryData`와 `summaryData2` 필드를 포함한 원본 JSON 구조를 그대로 유지합니다.

이 두 가지 작업이 완료되어야 해당 의사가 신규 의사로서 정상적으로 데이터베이스에 등록될 수 있습니다.

호출은 curl -X POST -H "Content-Type: application/json" -d '{"hid": "H01KR-11000001"}' http://localhost:1200/v1/c/crawling_did_link/find-past  로서 매번 hid는 변경이 되니 참고해야 한다
